## TG 聊天命令 `/search`（v1.5）

用户需求：给 bot 发 `/search` 就能查池子里的文件。

### 实现（全部在 `server/app.py`，未新增文件，故 deploy.sh 只需加测试脚本）

- `_bot_poll_loop()`：`getUpdates` 长轮询（25s），启动先 `deleteWebhook`；
  首次启动探最后一条 `update_id` 并跳过，避免重放历史积压；`offset` 存 `/opt/tgpool/tg_offset.json`。
- 命令：`/search`（文件名 + **目录名**双向匹配，目录命中时连带子目录）、`/ls [路径]`、
  `/get <编号>`、`/stats`、`/help`。
- 结果用 inline keyboard 编号按钮 + 分页（8 条/页，`editMessageText` 原地翻页不刷屏）。
- **投递用 `copyMessage`**（`from_chat_id` + `message_id`）→ 零带宽、零延迟；
  失败自动回退 `sendDocument(file_id)`（Telegram 同样复用文件，不重传）。
- 白名单鉴权：只响应 `TG_CHAT_ID` 与 `TG_BOT_ADMIN_IDS`，否则泄露整个文件清单。
- 新环境变量：`TG_BOT_POLL`（默认 1）、`TG_BOT_ADMIN_IDS`、`TG_BOT_OFFSET`。
- 新诊断接口 `GET /api/bot/status`（`token_ok` / `last_poll` / `handled` / `getme`）。

## 反向上传：发文件给 bot 即收录

用户接着问「在 tg 的 bot 上传文件可以吗」——可以，而且**服务器不传任何字节**：
文件发到 bot 时已经在 Telegram 上了，"上传"只是登记一条索引 + 写一条 journal。

### 实现

- `_incoming_file(msg)`：支持 `document`/`video`/`audio`/`animation`/`voice`/`video_note`/`photo`
  （`photo` 取最大尺寸；`sticker` 不算文件）。缺 `file_name` 时按类型生成
  （`audio` 用 title；`voice`→`.ogg`、`video_note`→`.mp4`、`photo`→`.jpg`）。
- 默认落点 `/收件箱`（`TG_BOT_INBOX` 可配）；**说明第一行若以 `/` 开头则当目标路径**，
  缺失目录用 `_ensure_folder_path()` 逐级自动创建。
- **按 `file_unique_id` 去重**，重复发送只提示不重复收录（备份池里静默翻倍是灾难）。
- 消息本来没有说明时才用 `editMessageCaption` 补 `TGPOOL <路径>`；**有说明绝不覆盖**。
- `_handle_message` 重构：**鉴权提前**到最前面，非文字消息路由到 `_handle_file_message`；
  未授权会话发来的文件同样不收录、不回复（避免对外暴露这是存储池）。

### 关键设计约束

`rebuild_index.py` 只认 `journal/index.jsonl`、**不认 caption**（已核对源码）——
所以反向上传写的是与网页上传**完全相同的一组字段**（含 `path`），否则灾备重建会漏掉这些文件。
目录自动创建时也要逐级写 `mkdir` 事件，否则重建时目录结构丢失。

### 测试与部署

- 自测从 48 项扩到 **74 项，全通过**：新增类型识别 9 项、入库/去重/路径/未授权 16 项、
  「收录后能被搜到并取回」2 项。
- `tgpool-deploy.tar.gz` v1.5 = 184,391 B，md5 `acf31184f2e6fedd07ede140624c506e`；
  本地 / `deploy/app/app.py` / 服务器 `/opt/tgpool/app/app.py`（md5 `82b246b2…`）/ `/root` 副本
  全部一致。已在 Telegram 会话存了一份（msg 54）。

## 模糊搜索统一层（v1.6）

用户问：bot 和网页的搜索能不能"只要包含关键词就显示"。实测结论：原来就是 `LIKE %kw%` 包含匹配，
但存在四个真实缺口，这次一并修掉：

- **`%`/`_` 未转义**（旧 SQL LIKE 当通配符，搜 `a_b` 会误中 `axb`）→ 改纯 Python 字面量匹配，天然消除；
- **网页搜不到目录名**（旧 web 只查 `files.name`，bot 才补目录）→ 统一规则；
- **无多关键词** → 空格分词 AND，词可分别落在文件名/路径；
- **无相关性排序** → 全等 > 前缀 > 名称包含 > 仅路径包含，同级 id 降序。

### 关键实现（server/app.py）

- `folder_path_maps(conn)`：一次解析整棵目录树 → `{fid: 路径字符串}` + `{fid: [{id,name}...]}`，
  避免逐文件递归查路径（O(n·depth) → O(n)）。
- `search_files(conn, query, limit)`：统一搜索引擎，返回 `(items, total)`；
  路径匹配天然覆盖"目录名命中"，旧 `_collect_hits` 的 folders 表查询整段删除。
- `/api/list?q=` 与 bot `_search_bot` 都走 `search_files`；bot 命中超 200 提示截断。
- 契约保持：网页 `path` 仍是 `[{id,name}]` 列表；bot 用 `path_str`。
- 前端：`hlFrag()` 用 DOM textContent 拼接做关键词高亮（免 XSS/实体问题，区间合并算法 node 验证过）；
  面包屑显示"N 个结果"；搜索结果所在路径可点击直达该目录。

### 验证

- 离线自测扩到 **88 项**（新增：路径片段命中、多关键词 AND、词分落名/路径、
  `_`/`%` 字面量、大小写、score 值域、limit 截断且 total 不变等 13 项），生产副本全过。
- 生产实测：`q=2026` 命中 `CUMCM2026Problems.zip`（/test）；`token_ok=true`、轮询心跳正常。
- 三方 md5 一致（app.py `b82f701c…`，index.html `589afca3…`）；备份 `*.bak-fuzzy-20260912`。
- 部署包 v1.6（187,502 字节，md5 `a59032ef…`）→ 本地 + `/root` + Telegram 云端（msg 57）。
- 经验：**往共享 fixture 加测试样本，会撑大后续统计断言的期望值**（这次 14→18、16→20），
  改完要么更新断言、要么把新样本隔离到独立测试块。

## /search back 排查 + /backups 命令（v1.7）

用户反馈 `/search back` "没有返回"。排查：日志显示消息已处理且 sendMessage 200 OK 送达——
回的是"没有命中任何文件"，因为索引里 9 个文件都不含 "back"。用户实际想找的是
`tgpool-backup-*.tar.gz`（每日备份包）：它们由 backup_index.py 直接调 Bot API 上传，
**不走收录流程，天然不在索引里**。属于预期差，不是 bug。

经用户选择（AskUserQuestion），实现 **/backups 命令**：

- 读 `backup/remote.jsonl` 注册表（backup_index.py 上传成功时追加：
  ts/at/name/size/file_id/message_id/sha256），列出最近 14 份（MAX_BACKUPS）。
- 点编号按钮（callback `b:<message_id>`）→ `copyMessage` 零带宽复制原消息回对话。
- **设计决策：备份包刻意不进池子索引**——若进索引，网页/bot 的删除会连带删掉
  Telegram 上的异地副本，反而削弱灾备。/backups 只读注册表，与删除链路完全隔离。
- 无记录/缺 message_id 均有兜底；/help 已更新；别名 /bk。

验证：93 项离线自测全过（新增 5 项：列表文案、缺 msgid 不出按钮、copyMessage 参数、空注册表提示）；
生产 md5 `fa3c4907…` 与本地/包内一致；用真实 remote.jsonl 向用户会话发了实弹列表（send 200 OK）。
部署包 v1.7（188,909 字节，md5 `062def3b…`）→ 本地 + /root + Telegram 云端（msg 61）。

新坑记录：
