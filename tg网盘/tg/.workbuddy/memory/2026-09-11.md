## 新增：索引灾备体系（当天完成，已做删库演练）

**关键结论（已实测验证，别再重复试）**：**Bot API 无法反向重建索引**。
- 没有列举历史/按 message_id 取消息的接口
- `getUpdates` 只返回"别人发给 bot"的消息，**bot 自己的 sendDocument 不在其中**
- 本地 bot API 落盘目录是 `file_0.bin` / `file_1` 这类**不透明文件名**，原始文件名也拿不到

所以方案改成「让索引始终可重建」，三层：

| 层 | 位置 | 作用 |
|---|---|---|
| journal | `/opt/tgpool/journal/index.jsonl` | 每次改动追加一行，**永不截断**，可完整重放（零丢失） |
| 本地备份 | `/opt/tgpool/backup/tgpool-backup-*.tar.gz` | 含 index.db + journal + MANIFEST，保留 14 份 |
| 远程备份 | 同一份发到 Telegram 会话 | 防整盘损坏；可 `--fetch` 取回，也可在 Telegram 客户端手动下载（不需要 token） |

**journal 设计要点**：目录用**路径字符串**记录而非自增 id，重放不依赖任何 id 映射；
文件用 db id 记录，所以**重建后文件 id 不变**（下载链接照旧），但**文件夹 id 会重新分配**。

**新增文件**
- `server/tools/rebuild_index.py`：`--seed`（从现有库导出日志起点，首次必备）/ `--verify` / `--stats` /
  `--restore <db>` / 默认从 journal 重建（原库自动另存 `index.db.bak-<ts>`）
- `server/tools/backup_index.py`：备份、`--list`、`--fetch`、`--prune-remote`
- `scripts/install_backup.sh`：部署工具 + seed + 写 `/etc/cron.d/tgpool-backup`（每天 03:30）
- `scripts/test_dr.py`：完整灾备演练脚本
- `scripts/fix_cron.sh`：重写 cron（用 sed 从脚本里抠 cron 内容会把 `cat > ...` 也抠进去，别那么干）

**app.py 改动**：所有写操作调 `jlog()` 追加日志；上传时附 `TGPOOL /路径` caption（`TG_CAPTION_PATH` 可关）；
**新增同级目录同名约束（409）**——否则路径不唯一，重建时同名目录会被合并（这是演练中真实暴露的缺陷）。

**演练结果**：删掉 `index.db{,-wal,-shm}` → 从 journal 重建 → 3 目录/5 文件完全一致，
文件 id 保持（12、13），下载 sha256 一致。远程备份 `--fetch` 取回并 sha256 校验通过。

**又一个 `--local` 模式的坑**：`--fetch` 起初 404，因为拿 `getFile` 返回的 `file_path` 拼 HTTP URL。
`--local` 模式下它返回的是**本机绝对路径**（`/var/lib/telegram-bot-api/.../documents/file_N.gz`），
必须**直接读磁盘**。这与 app.py 里 download 的处理是同一个坑，第二次踩到。

**待办/风险**：`tgpool.env`（bot token）不在备份包里——整盘损坏后若 token 也丢，
备份虽在 Telegram 里可直接手动下载，但无法重建服务。建议用户单独保存 token。

## deploy.sh v1.1 —— 修复「apt 源」步在全新机器上的误判

**现象**（用户在新服务器上）：`[2/10] apt 软件源` 打印 4 个镜像全部 `99s`，
随后 die「所有 apt 镜像都不可达」。

**根因**：`step_apt` 用 `curl` 探测镜像，但 `curl` 要到**第 400 行才安装**。
全新系统没预装 curl 时，每个探测瞬间失败 → 全部落到 `... || echo 99`
这个**写死的占位值** → 被误判成"所有源都不可达"。
**99 是常量，不是耗时**——所以 4 个"耗时"才会一模一样。

**修复（SCRIPT_VER 1.0 → 1.1）**：
1. 新增 `_probe <host> <cn>`：逐级退回 **curl → wget → bash 内建 /dev/tcp**，
   失败时回显 `FAIL:<原因>`（DNS 解析失败 / 连接被拒 / 超时(12s) / TCP 80 不通），
   不再把不同故障混成一个 99。
2. 全失败时打印**可直接复制**的排查命令（curl wget / resolv.conf / getent / /dev/tcp）。
3. apt 源改为幂等：已指向同一镜像时 `skip "apt 源已经是 X，无需改动"`。
4. `apt-get update` 失败改为**致命**，打印日志末尾 + 排查提示；
   新增 `TG_FORCE_MIRROR=1` 强制换源开关（已写入 usage）。
5. 镜像候选去掉 archive.ubuntu.com（它已作为"默认源"单独测过）。

**实测**（在仍在线的那台老服务器 82.158.224.64 上）：
- `--check`：真实耗时 aliyun 0.48s / tuna 2.24s / ustc 1.29s，
  显示 `默认源不可达（超时(12s)）`，并正确 skip「apt 源已经是 mirrors.aliyun.com」。
- 退回路径（抽出线上 `_probe` 注入假 PATH 实测）：
  有 wget → aliyun `0.47` / archive `FAIL:wget 失败(码 124)`；
  无 curl 无 wget → aliyun `0.02`（TCP 通）/ archive `FAIL:TCP 80 不通`。
  三种工具条件下都能正确判定"该换 aliyun"。

**教训（通用）**：
- **探测工具必须先于探测存在**。拿"本机还没装的工具"做前置检测，在全新机器上会集体失败，
  再被兜底值掩盖成错误结论。
- **兜底值不要用看起来像真实数据的数字**（`99` 会被读成 99 秒），要用显式 `FAIL:原因`。

**状态**：老服务器仍在线正常服务（3 文件 / 1 目录）；用户那台新服务器 IP 未知，
待其反馈排查结果。DEPLOY.md「常见报错」已补 3 行新故障。

## 换服务器后"网页列表为空"——已确认为预期行为（非遗漏）

**用户反馈**：新服务器部署完，网页上没有旧文件；但文件本体还在 Telegram 里，
老服务器网页上仍能看到并下载。

**结论：正常现象，不是 bug。** 网页列表读的是服务器本地的 `index.db`（文件夹 + 文件索引），
它**不在 Telegram 里**。新机器 = 空账本 → 列表为空。而 Bot API **无法列举历史消息、
bot 也收不到自己发的消息**（早已实测验证），所以新机器不可能自动发现 Telegram 里的旧文件。

**解法**：把旧机器的索引迁过去（老机器还活着时最快）。
```bash
# 在新服务器上
scp root@82.158.224.64:/opt/tgpool/backup/tgpool-backup-20260911-080137.tar.gz /root/
cd /root/tgpool-deploy && bash deploy.sh --bundle /root/tgpool-backup-20260911-080137.tar.gz
```
`step_restore`（第 7 步）会 sha256 双校验 → 停服务 → 原索引另存 → 落盘 index.db+journal → 起服务。
**顺序是内置的**（第 7 步恢复早于第 10 步启用灾备），所以不会出现"journal 拿空索引做起点"。

**核实过的事实**（老服务器 `tgpool-backup-20260911-080137.tar.gz`）：
- MANIFEST：1 目录 / 3 文件 / 1,026,232 字节
- 包内 index.db：folders=[(1,'test')]，files=[(4,'12.pdf',511716),(5,'12.pdf',511716),(6,'connecting_sever.sh',2800)]，
  message_id = 6 / 7 / 8；journal 19 行；`--verify` 通过
- `step_backup` 用 `[ -s journal ]` 判断，非空就 skip `--seed` → 恢复后再跑 `--bundle` 是安全的

**前提条件**：新机器的 **bot token 必须与旧机器相同**（`file_id` 是 bot 维度的），
`TG_CHAT_ID` 也要是同一个会话；否则列表能恢复但下载会 404。

**教训**：索引是**单机状态**。换机重建时，"服务能起来"≠"数据可见"——
`--bundle` 这一步不是可选项，忘了它就会得到一台空池子。已在 DEPLOY.md「常见报错」加两行。

## 18:35 · 压测：手动备份索引的耗时/资源随文件数的伸缩性

**问题**：手动备份会不会因为文件多而变慢？9000 文件 + 1000 目录要多久？

**结论**：慢是"体积变慢"不是"数量变慢"。备份**不遍历文件本体、不逐个请求 Telegram**，
只打包 `index.db + journal` 并发**一次** `sendDocument`。耗时 ≈ 正比于**索引体积**（≈ 正比于文件数，系数极小）。

**实测**（老服务器 82.158.224.64，1 vCPU / 971MB）：
| 规模 | index.db | journal | 合计 | 包大小 | 本地打包 | 上传 | 总计 |
|---|---|---|---|---|---|---|---|
| 9000 文件 / 1000 目录 | 1.82 MB | 3.25 MB | 5.08 MB | 2.06 MB | 0.99 s | ~2.2 s | **3.17 s** |
| 45000 / 5000 | 9.07 MB | 16.31 MB | 25.4 MB | 10.3 MB | 2.98 s | ~11 s(推算) | ~14 s |

- 本地打包各阶段（本机 9000 文件，合计 0.66-0.87s）：sqlite backup 113ms / integrity 10ms /
  COUNT 16ms / sha256(db) 4ms / sha256(journal) 14ms / **tar.gz 452ms（大头）** / 读包 12ms / 解包算caption 26ms
- 服务端 `resource.getrusage` 峰值 **RSS 25.1 MB**，CPU 1.02s → 内存/CPU 完全不是瓶颈
- **瓶颈是上传带宽**：2.1MB / 2.2s ≈ **1 MB/s**
- 压缩率稳定 **2.5x**；线性性已用 5x 数据点验证（体积 5.0x，耗时 3.4x）
- 单文件成本：库 ~200 B/文件，journal ~360 B/操作
- **journal 才是体积大头**（3.25MB vs 库 1.82MB），因为每条 `add` 都完整存 86 字符 file_id；
  且 journal append-only 永不截断 → 它随**历史累计操作数**增长，不只是当前文件数

**结论数字**：9000 文件 + 1000 目录 → **约 3 秒**（1 核小机器），远低于接口 300s 超时预算。
保留 14 份 × 2.06MB ≈ 29MB 长期磁盘占用。90,000 文件估算 ~28s，仍在安全区。

**清理**：压测在 `/tmp/bench` 沙箱用 `TG_DB_PATH/TG_JOURNAL/TG_BACKUP_DIR` 隔离，**未碰线上索引**；
测试产生的 Telegram 消息 msg 32/33 已用 deleteMessage 删除，`/tmp/bench` 已删；线上 stats 验证完好。

## 20:05 · 定位「点大文件下载要转很久才开始」的根因（首字节延迟）

**用户问题**：为什么点一个大文件下载，要转很久才开始？

### 结论：不是网络慢，是 bot API 必须"整份拉完"才给路径
实测（老机 82.158.224.64，22.34MB PDF，id=15 / id=20）：

| 场景 | TTFB（首字节） | 总耗时 |
|---|---|---|
| 首次下载（清掉缓存） | **40.46 s** | 40.52 s |
| 第二次（已缓存） | **0.013 s** | 0.076 s |

→ **TTFB ≈ 总耗时**，即 99.8% 时间花在"还没开始"。传输本身只 0.066 s。

### 机制（用 2.5s 采样抓到全过程）
- `/api/download/{id}` → FastAPI 调 bot API `getFile`
- **`getFile` 会阻塞直到整份文件落到服务器磁盘**
- 采样实测：TDLib 先写到 **`<token>/temp/24`**，以 ~590 KB/s 稳定增长
  （1507328 B / 2.5s ≈ 590 KB/s），40 s 后满 23425277 B，
  **然后原子改名为 `documents/file_24.pdf`**（瞬间完成）
- 路径返回后 FastAPI 才开始向浏览器发首字节；因文件已在本地磁盘，后续 307 MB/s

### 顺带查清的几件事
- **缓存文件名不稳定**：`file_N` 的 N 是**下载完成时才分配**的序号，
  重下一次会换新名字（id=15 曾映射 file_14 → file_18 → file_24）。**不能靠固定路径追踪**
- **没有内容去重**：id=15 与 id=20 是同一份 PDF 的两次上传，各自独立缓存（file_18 / file_19）
- `temp/` 平时为空，只在下载期间出现增长文件 → **可用来做进度观测**
- 之前误判过一次：以为 temp/ 不写盘，实际是我删错了目标文件（映射已变），
  getFile 命中旧副本 0.01s 返回，导致采样全是静止值

### 为何不能"边下边传"
Bot API 的 `getFile` 没有流式/Range 接口，只返回本地文件路径；
该路径只有在文件完整落盘后存在。自建 `--local` server 已是此架构下最优。
⇒ 首次下载的等待是**架构固有**的，无法消除，只能改善体验（进度反馈 / 提前预热）。

**换算**：578 KB/s 下 2GB 首次点击要等约 1 小时。

## 20:20 架构答疑：能否绕过服务器直连 TG + 发现 token 已失效

- 用户问「能不能不经服务器，直接用 bot 对接 tg，在网页上传下载」。结论：技术上可行但不该做。
  服务器三职责中只有「转发字节」可省，且必须放弃 local 模式。
- **实测证据（在服务器 82.158.224.64 上 curl）**：
  - `api.telegram.org` 返回 `access-control-allow-origin: *`
    → 浏览器 JS 确实能跨域直连 Bot API，无需后端。这就是"技术上能"的依据。
  - 但官方托管 API 上限：上传 50MB / getFile 下载 20MB；只有自建 `--local` 才能到 2000MB。
  - 托管模式有 CDN 直链可 302 重定向；**local 模式 getFile 返回本地磁盘路径
    （/var/lib/telegram-bot-api/<token>/documents/file_N.pdf），不存在可重定向的 Telegram URL**
    → local 模式下「下载不过服务器」物理上做不到。这是本次最关键的技术判断。
- 三大 blocker（按严重度）：① token 必须在服务端（前端明文 = bot 完全失守，Bot API 无权限粒度）；
  ② 50MB/20MB 上限否决大文件；③ 丢失 index.db/文件夹/journal（Bot API 无列举能力），
  而索引层才是本项目核心价值，比带宽值钱。
- **⚠️ 意外发现：bot token 已失效**。`getMe` 与 `getChat` 对官方 API 和本地 8081 均返回
  `401 Unauthorized`；最后一次成功上传是 11:23:54 UTC（约 1 小时前）。
  12:16 UTC 的下载成功是因为文件已在本地缓存，getFile 走本地磁盘无需联系 Telegram。
  → 池子处于「仅缓存命中可用」的降级状态，新上传与未缓存下载会失败。
  需用户确认是否主动重置了 token；若重置需同步 `/opt/tgpool/tgpool.env` 并重建 docker 容器 `tg-bot-api`。
- 服务角色澄清：`telegram-bot-api` systemd 单元显示 inactive 属正常——Bot API 实际由
  docker 容器 `tg-bot-api`（aiogram/telegram-bot-api:latest）提供，docker-proxy 监听 127.0.0.1:8081。
  排查服务状态时应查 docker ps 而非仅看 systemd。
- 服务端路由实际为 `/api/list`、`/api/stats`（不是 /api/files）；两者均需 Basic auth，
  本地 curl 无凭据会返回 401 Not authenticated。
